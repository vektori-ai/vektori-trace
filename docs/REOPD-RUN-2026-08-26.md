# ReOPD run and first evaluation — 2026-08-26

Status: complete. Artifact produced, screened on four S16 diagnostic tasks.
Nothing running; all endpoints torn down.

## Headline

The ReOPD arm trained to completion and produced `a_reopd`. On the four
diagnostic tasks it **did not improve on its own parent checkpoint**, and it
introduced a new, reproducible failure: **the policy enters infinite reasoning
loops**, generating until the output cap and returning an empty message that
Tau2 refuses to grade.

The loop is the substantive finding of the day. It is not a cap-sizing problem
and cannot be fixed by raising the cap.

## 2. Evaluation result

Four S16 diagnostic tasks (57, 73, 75, 93), `--num-trials 2`, temperature 0,
`max_output_tokens` 2048.

| Task | ReOPD | A_warm baseline |
|---|---|---|
| 73 | **1.0** | passed (handoff) |
| 75 | **1.0** | passed (handoff) |
| 93 | **0.0** | 0.0 (measured, ck35 and ck70) |
| 57 | ungradeable | not tested |

Gradeable: **4 of 7 episodes**. Three episodes died from the loop below.

**No measurable gain over CK35 on any task where a comparison exists.** That is
the §10 "SFT works but replay OPD does not gain" row.

### Caveat that must travel with this result

`A_warm` has **not** been evaluated under this harness on these tasks. The
baseline column comes from `SOL-HANDOFF.md` and a different run on a different
day. Until CK35 is run on the same four tasks with the same settings, "ReOPD
caused X" is a hypothesis, not a finding. That comparison costs ~$1.

These four tasks are also the *contaminated diagnostics* (§4.2): CK35 was
selected partly on 73/75/93, which biases `A_warm` upward. Since all three arms
inherit CK35, this cancels for ReOPD-vs-SFT but not for ReOPD-vs-A_warm.

## 3. The reasoning loop

Captured directly by patching Tau2 to write every raw response *before*
validation (previously the failing response was discarded with the exception).

```text
[0] finish=stop        reasoning=   250ch content= 138ch  ctok=    90
[1] finish=stop        reasoning= 1,943ch content= 137ch  ctok=   459
[2] finish=stop        reasoning=   308ch content= 108ch  ctok=   103
[3] finish=tool_calls  reasoning= 2,989ch content=   0ch  ctok=   797
[4] finish=length      reasoning=47,338ch content=   0ch  ctok=11,434  EMPTY
```

Row 4 is the failure. The tail repeats three sentences verbatim:

> *"But according to the policy, the order ID must have the '#' symbol. So the
> correct order ID is #W4284542. Therefore, the user's order number is missing
> the '#' symbol. So I need to inform them..."*

**Trigger:** the user said `order W4284542`; the retail policy formats order ids
as `#W4284542`. The model looped on whether to add the `#`.

Three numbers settle the diagnosis:

- `completion_tokens = 11,434` against a **2048** cap — a 5.6x overshoot. No cap
  value fixes this; raising it to 4096 only doubled the time to fail.
- `prompt_tokens = 4,950` against a 14,336 budget — **not** a context problem.
- `finish_reason` is `stop`/`tool_calls` on healthy turns — **not** a
  reasoning-parser misconfiguration.

Reasoning dominates output even on healthy turns: **64%, 93%, 74%, 100%** of
generated characters. The model sits close to the cap on every turn, so a loop
only has to start for the turn to be lost.

## 4. Bugs found and fixed

All five were caught by existing guards before corrupt data entered a gradient.

| Commit | Bug |
|---|---|
| `58f669a` | endpoint gate checked the reported window but not the advertised **input cap**; a 20480 window advertises only 12,288 input tokens, under the 12,880-token longest C30 prefix |
| `10dd3c9` | the gate's probe generated 2,048 tokens (33.9s) and blew its own 30s timeout, refusing a healthy endpoint |
| `37d9ae9` | the driver never passed `device` to the trainer, so no ReOPD run could reach the optimizer |
| `1e63b6e` | Qwen token bytes derived by per-token decode lost UTF-8 characters split across tokens |
| `f3a1983` | same defect on the **teacher** side; DeepSeek loads as a bare `tokenizers.Tokenizer` with `id_to_token`, not `convert_ids_to_tokens`, so the first fix missed it |
| `1f22c66`, `3dc68ec` | a repaired score row was rejected by a duplicate-key validator, blocking every resume |

The emoji that broke training at update 14 came from the teacher: 29 emoji
across 542 assistant messages in `flash_retail_p1.json`, which is part of the
training corpus. The student reproduces the habit at a similar rate (~4.5%).
Emoji are not a defect — the byte-extraction was.

Eval harness additions: `--adapter name=path` (the three arms live in
incompatible directory layouts), volume-side adapter validation, an
adapter-effect probe that refuses any arm whose logits match A0, and
`--generation-reserve`.

## 5. Why a null result was the expected outcome

From `opd_correct_recipe` (researched 2026-08-13):

> TML ran 64 prompts x 4 samples = 256 sequences/step for ~150 steps
> (~38,400 graded sequences) from a 400K-example SFT checkpoint.

This run: **512 graded sequences over 32 steps**. Roughly **75x fewer sequences**
and **5x fewer steps** than the reference recipe. The same note records the
previous null result's cause as "scale/staging, not implementation."

A null result at this scale is what the prior research predicts. It should be
reported as such rather than treated as an unexplained failure.

## 7. What to do next

Ranked by information per dollar.

1. **Run `A_warm` (CK35) on tasks 73/75/93** (~$1). The only way to know whether
   ReOPD helped, hurt, or did nothing. Every claim in §2 and §3 is conditional
   on this.
2. **Evaluate `a_sft_new_ck35_r2`** (~$1). It is genuinely budget-matched, so
   this is the §7 method comparison the experiment exists to make.
3. **Address the loop** — it is a sampling/decoding problem, not a cap problem.
   Candidates: a repetition penalty, `presence_penalty`, or capping reasoning
   separately from content. Worth testing whether CK35 loops too before
   attributing it to ReOPD.
4. **Do not scale up ReOPD** until 1–3 are answered. At 75x below the reference
   recipe, more updates at this scale are unlikely to change the outcome.
